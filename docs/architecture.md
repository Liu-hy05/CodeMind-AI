# CodeMind AI系统架构设计文档

## 1.系统整体架构

CodeMind AI采用分层架构设计，将系统划分为：

* 前端展示层
* 接入层
* 业务服务处
* AI能力层
* 数据存储层

整体架构：

```
用户
↓
Frontend Web
↓
API Gateway
↓
Backend Services
├── User Service
├── Knowledge Service
├── AI Service
└── Agent Service
↓
Data Layer
├── MySQL
├── Redis
└── Milvus
↓
LLM Models
├── GPT
├── DeepSeek
└── Qwen
```

---

## 2.个模块职责设计

### 2.1 Frontend Web

职责：

负责用户交互。

主要功能：

* 用户登录
* 文件上传
* AI对话
* 知识库管理
* 查看分析结果

前端不直接调用大模型。

所有请求经过后端处理。

### 2.2 API Gateway

职责：

作为系统统一入口。

只要功能：

#### **请求路由**

将请求转发到对应服务。

例如：

用户管理：

```
/user/**
```

进入：

User Service

AI请求：

```
/chat/**
```

进入：

AI Service

#### 权限控制

验证用户身份。

例如：

普通用户：

只能查询。

管理员：

可以上传知识库。

#### 服务治理

包括：

- 请求日志
- 限流
- 统一异常处理

### 2.3 User Service

负责用户相关业务。

功能：

- 用户注册
- 用户登录
- 用户权限管理

数据：

MySQL。

原因：

用户数据属于核心业务数据，需要持久化保存。

### 2.4 Knowledge Service

负责企业知识库管理。

功能：

- 文件上传
- 文件解析
- 文档管理
- 知识库构建

处理流程：

```
用户上传文件
↓
文件解析
↓
文本切割
↓
Embedding
↓
保存向量
↓
Milvus
```

### 2.5 AI Service

负责大模型调用。

职责：

- Prompt管理
- 模型调用
- 上下文管理
- AI响应处理

通过AI Gateway统一访问不同模型：

```
AI Service
↓
AI Gateway
↓
GPT / DeepSeek / Qwen
```

### 2.6 Agent Service

负责智能任务执行。

例如：

代码分析：

```
用户请求
↓
Agent
↓
调用代码搜索工具
↓
分析结果
↓
生成报告
```

未来支持：

- Bug分析
- 测试生成
- SQL生成

## 3. 数据存储设计

### 3.1 MySQL

存储结构化业务数据。

包括：

- 用户信息
- 权限信息
- 聊天记录
- 文件元数据

选择原因：

业务数据结构明确，需要事务和持久化能力。

### 3.2 Redis

存储高频访问和临时数据。

包括：

- 登录Token
- 热点问题缓存
- AI结果缓存

选择原因：

Redis基于内存存储，可以降低数据库压力，提高响应速度。

### 3.3 Milvus

存储企业知识向量。

包括：

- 文档向量
- 代码语义向量
- 历史问题向量

选择原因：

传统数据库只能进行关键词搜索，无法理解语义相似关系。

Milvus通过向量检索实现语义搜索。

## 4. AI问答流程设计

用户输入：

```
订单退款失败怎么办？
```

系统流程：

```
用户问题
↓
Backend接收请求
↓
权限验证
↓
知识库检索
↓
Milvus寻找相关内容
↓
组合Prompt
↓
调用LLM
↓
生成答案
↓
返回用户
```

---

## 5. 为什么需要知识库检索

直接调用大模型存在：

### 幻觉问题

模型可能生成不存在的信息。

### 企业知识缺失

公共模型不知道企业内部：

- 代码
- 文档
- 业务规则

### Token成本问题

不能将所有企业资料全部发送给模型。

通过RAG：

只检索相关内容，提高准确率并降低成本。

---

## 6. 为什么采用模块化设计

系统拆分多个服务：

```
User Service
Knowledge Service
AI Service
Agent Service
```

原因：

### 降低复杂度

不同功能职责明确。

### 方便维护

问题定位更加准确。

### 支持扩展

未来可以独立扩容某个服务。
